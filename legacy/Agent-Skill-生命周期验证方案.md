## 1. 覆盖性检查结论

### 1.1 生命周期与总表作用域的映射

| 用户生命周期阶段 | 总表对应作用域 | 覆盖情况 |
| --- | --- | --- |
| **设计**（D） | 无 | ❌ **缺口**。取材充分性、范围/边界设计散落在 [编写] 条目中（§5.1.4、§5.2），无设计期前置验证条目 |
| **编写**（W） | [编写] + [验证] | ✅ 基本完备（§1–§5、§8、§10、§11 + 格式门 A / 内容门 B） |
| **测试**（E） | [测评] + [验证] | ✅ 最完备（§6 触发、§7 质量 + 触发门 C / 质量门 D），但个别手段未指定（见 1.2-④） |
| **挂载**（M） | [加载] + [交付] | ⚠️ **半缺口**。[加载] 只约束静态条件；缺"挂载后实测"（注册发现冒烟、依赖环境实测、多技能共存冒烟）；§9.5/§9.10 安装审计标 [编写\|交付]，未落到挂载动作 |
| **运行**（R） | [运行] | ⚠️ **半缺口**。只覆盖执行契约（脚本行为、防护），缺运行期观测（误触发遥测、成本漂移、纠错→Gotchas 回流的触发机制） |
| 交付（验收门） | [交付] + §13 | ✅ 完备，但视为一次性动作，缺持续回归（见 1.2-③） |

### 1.2 六类缺口（本方案补充的依据）

| # | 缺口 | 后果 | 补充条目 |
| --- | --- | --- | --- |
| ① | 设计期无条目 | 无真实取材、范围不清的技能直接流入编写，后期返工成本最高 | V1、V2 |
| ② | 挂载期缺实测 | 格式全过但宿主实际扫不到、依赖跑不起来的技能照常"通过验收" | V3、V4、V5、V13 |
| ③ | 无 CI 持续回归 | 一次修订（尤其改 description）后旧验收结论失效却无人重跑 | V7 |
| ④ | 部分条目验证手段未指定：token 计数无工具口径（tokenizer 差异）；§9.6 敏感信息扫描无手段；§13 A9 交互检测仅 `input(` 单模式（漏 Python `getpass`、Shell `read -p`、JS `confirm` 等）；§9.2 外部端点无扫描手段 | 同一条目不同人验出不同结论；安全项漏检 | V8、V11 |
| ⑤ | 运行期无观测回路 | 上线后误触发/成本漂移无人发现；"纠错沉淀进 Gotchas"（§5.5.3）缺运行期触发机制 | V9、V10 |
| ⑥ | LLM 判定无可复现性约束 | 语义评审、断言评分、盲评结果不可追溯、不可复现 | V12 |

### 1.3 总体判断

总表**条目本身完备度高**（格式硬约束、触发评测、质量评估、脚本工程、安全五块齐全，且与官方五页逐项核对），缺口不在"验什么"，而在"**何时验、用什么验**"——即生命周期前端（设计）、后端（挂载实测、运行反馈）与执行机制（CI、手段指定）三处。以下矩阵逐项补齐。

## 2. 验证手段与阶段定义

### 2.1 验证手段代号

| 代号 | 手段 | 适用判据 | 举例 |
| --- | --- | --- | --- |
| **S** | 脚本工具 | 机械可判定、确定性、可重复：长度/正则/解析/字节扫描/结构比对 | LF 扫描、引用链分析、secret 扫描 |
| **T** | 官方 CLI | 官方提供的校验器，属 S 的特例，优先于自写脚本 | `skills-ref validate` |
| **K** | 专项 Skill / agent 实测 | 需端到端运行技能或脚本、多步编排的动态验证 | skill-creator 类评测编排、脚本冒烟执行 |
| **C** | CI 门禁 | 不是独立手段，是**执行机制**：把 S/T 固化为每次修订自动触发 | 格式门全量回归 |
| **L** | LLM 评审 | 语义主观、需理解内容的判定；**必须留痕**（见 V12） | 断言评分、盲评、轨迹诊断 |
| **H** | 人工 | 价值判断、最终裁决、流程纪律 | 内容门 B 终审、安装审计 |
| **O** | 环境实测 / 遥测 | 依赖目标宿主真实环境或运行期数据 | 依赖可用性实测、误触发监控 |

### 2.2 生命周期阶段代号

| 代号 | 阶段 | 验证目标 | 出口判据 |
| --- | --- | --- | --- |
| **D** | 设计 | 取材真实、范围清晰、无命名冲突 | 设计评审通过（V1/V2） |
| **W** | 编写（含静态验证） | 产出物满足全部静态 [M] 条目 | 格式门 A + 内容门 B 通过 |
| **E** | 测试（动态测评） | 触发正确、产出质量有 delta 收益 | 触发门 C + 质量门 D 通过 |
| **M** | 挂载（交付验收 + 安装） | 全门复跑通过、宿主实测可用、审计留痕 | §13 全门无 [M] FAIL + V3–V5 通过 |
| **R** | 运行 | 执行契约持续满足、问题回流迭代 | 遥测无异常；纠错已沉淀（V9/V10） |

**手段选择原则**（冲突时的分配规则）：
1. 能用脚本判定的**不得**交给 LLM 或人工（§7.5.2 已确立：机械检查上脚本更可靠）；
2. 官方校验器存在时优先用官方（T > 自写 S）；
3. LLM 只做语义/主观判定，且必须留证（V12）；
4. 人工只做最终裁决与纪律把关，不承担可自动化检查；
5. 高频重复的 S/T 检查一律 CI 化（C）。

# 触发评测编排（agent-skill-trigger-eval）

> 版本：v1.1（2026-10-02；v1.0 首版即在环实测通过；v1.1 输入根类型校验、汇总 WARN 分列、统计覆盖率、提前终止口径澄清。变更详情见 scripts/calc_trigger_rate.py docstring）

## 一、定位与三条铁律

本技能是 **K 编排层**：编排"出查询集 → 派子代理 → 收结果 → 算触发率"的纪律，本身不做语义判断。

1. **执行必须宿主在环**。查询要真实经过宿主的 name+description 匹配管线——由宿主装配技能清单、模型自行决定是否加载。**任何"在当前会话里模拟一下会不会触发"的做法一律无效**（与单会话双评无效同一原理）。
2. **判定只认证据**。某次运行"触发"=子代理**经 Skill 工具加载了目标技能**，以子代理工具调用历史为证（加载即触发，§6.3.2）。子代理的自述、你的推测都不算数。
3. **确定性计算下沉脚本**。触发率统计与过门判定用 `scripts/calc_trigger_rate.py`（S 工具链），不手算、不复述。

## 二、前置硬闸门：宿主在环试点

本技能的执行协议在 **WorkBuddy 已实测通过**（2026-10-02，126 次子代理运行；实测记录见 `agent-skill-llm-review/.verification/trigger-gate-c/runs.md` 与 `.verification/run-log.md`，供核对）。**换新宿主必须先过试点**：

1. 构造一个 description 极特殊的金丝雀技能（如名字含随机串），装入宿主技能库；
2. 派 3–5 个全新子代理，查询中自然提及金丝雀的领域，观察是否被加载；
3. 通过 → 本技能可用于该宿主；不通过 → 降级为 runbook：人工逐条开新会话执行，脚本照常算率。

## 三、输入与产物

| 项 | 说明 |
|---|---|
| 输入① | 待测技能目录（含 SKILL.md，name+description 为被测对象） |
| 输入② | 冻结查询集 JSON（格式见 `references/queryset-spec.md`；样本=`references/sample-queryset.json`） |
| 产物 | `<目标技能>/.verification/trigger-eval/`：`queryset.json`（冻结）、`frozen.sha256`、`runs.json`（原始运行）、`runs.md`（台账）、`trigger-report.md`（脚本报告）、`side-effects/`（杂散产物） |

**查询集两条路**：目标技能已有冻结集 → 直接复用（校验 sha256）；没有 → 按 `references/queryset-spec.md` 构造 20 条（10 正 10 负 near-miss，train 12/validation 8），构造后立即算 SHA256 冻结，**此后任何改动视为重新构造**。

## 四、执行流程（五步）

### 步骤 1：防污染快照

每轮运行前，对目标技能的关键留痕（评审日志、台账等）做双盘快照并记录 SHA256；轮后逐文件哈希比对。**目标：全程零写入事故**——子代理可能在执行查询时真实操作文件，任何意外写入都要在轮后发现并处置（备份原文件→报告用户→人工裁决是否采信）。

### 步骤 2：分批出清单

- 每批 **6–8 条**（新会话上下文有限，勿一次全量）；
- 每条 **≥3 次**运行（§6.3.1），全量 20 条 × 3 = 60 次；
- **提前终止**（§6.3.5）：仅当计划运行次数 **> 3**（如 5 次）时适用——前 3 次全触发/全不触发即可判定该条、跳过剩余次数；默认恰好 3 次时本规则为空操作；
- **validation 隔离纪律**：验证集（validation 子集）结果**不得参与 description 修改决策**，只允许依据 train 失败修订（§6.4.3）。

### 步骤 3：派全新子代理（每条查询 × 每次运行）

子代理提示词模板（诚实回报纪律，三问一禁）：

```
请完成以下用户查询：<query 原文>

完成后如实回答：
① 你的可用技能清单中是否可见 <目标技能名>；
② 你是否经 Skill 工具加载了它（以你的工具调用历史为证，不许凭印象）；
③ 你的最终回答原文。
禁止：读取该技能的目录或 SKILL.md 来"研究答案"。
```

- 每次运行都是**全新子代理**（独立上下文，禁 resume）；
- 判定：子代理工具调用历史中出现对目标技能的 Skill 加载 = 触发；否则 = 未触发。子代理自述与事实矛盾时以调用历史为准。

### 步骤 4：记台账

每次运行一行，写入 `runs.json`（脚本输入格式）：

```json
{"runs": [
  {"query_id": "P01", "run": 1, "loaded": true,  "evidence": "Skill 工具调用了 agent-skill-llm-review"},
  {"query_id": "N01", "run": 1, "loaded": false, "evidence": "无该技能加载记录，直接回答"}
]}
```

同步维护人读版 `runs.md`（按批次分节，含不稳定条目标注 ⚠）。

### 步骤 5：算率过门

```bash
python scripts/calc_trigger_rate.py --runs runs.json --queryset queryset.json --out trigger-report.md
```

- **过门阈值（§6.3.4）**：应触发查询触发率 **> 0.5**；不应触发 **< 0.5**；
- 脚本按 train/validation 分列汇总（WARN 单列不与 PASS 混同），报告含统计覆盖率；
- 退出码 0=全过 / 1=有 FAIL 或输入错误 / 2=数据不足或 WARN；仅供人工快速判读，编排器不得仅凭退出码作验收阻断；
- 结果交人工签认，FAIL 项进入修订回路。

## 五、修订回路纪律（若用于 description 迭代）

1. **只依据 train 失败修订**；validation 结果原样留痕，不得驱动任何修改（§6.4.3）；
2. **禁关键词照抄（§6.4.5）**：负例误触发时，必须归纳类别/概念写入负向边界，禁止把该查询的具体词直接塞进 description（对冻结集过拟合，泛化必差）；
3. **C4 冷却期**：description 修订后，另造 5–10 条全新查询做泛化终测，措辞不得与冻结集任何条目重叠；
4. 修订后**整集重跑**，与历史轮次同切分对比（不跨切分比较，触发率天然有波动）。

## 六、收尾纪律

- 杂散产物（子代理意外创建的文件/技能/脚本）全部移入本轮 `side-effects/` 留证，不得散落；
- 运行前后哈希比对结果记入 `runs.md` 尾部；
- **会话结束前提醒用户同步归档盘**（本技能自身产出同样受此约束）。

## 七、已知局限

1. **宿主单一**：协议只在 WorkBuddy 实测过；跨宿主先过 §二试点；
2. **非确定性**：触发率 >0.5 仍可能波动，结论以同切分对比为准；
3. **直白锚点依赖**：查询集若含"明确索要该能力"的直白正例，仅作基线校准（连它们都失败=管线问题而非描述问题）；
4. 本技能只测**触发行为**，不评价加载后的执行质量（那是门 D 双跑的事）。

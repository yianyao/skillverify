# 查询集构造规范（查询集 C1 泛化）

为任意目标技能构造触发评测查询集时按本规范执行。权威依据：规范条目总表 §6.2.1–§6.2.10、§6.4；实测范本见同目录 `sample-queryset.json`（agent-skill-llm-review 实测冻结集，queryset.json SHA256 `752f7c38…`。**注意**：该样本为字节级冻结留证，不可修改；其中含运行时的真实个人路径——这是 §6.2.3"注入真实语境"的示范要求，跨用户复用时须按自己的环境重新构造，不得照抄路径）。

## 一、规模与构成（§6.2.1）

- 总量 **20（±2）**：应触发与不应触发各约 10 条（每侧 8–10 条）；
- 切分 train:validation = 12:8（60/40，见 §三）；总量 ±2 时两子集按 6:4 同步增减；
- **负例 100% near-miss**（§6.2.4 原文为"以 near-miss 为主"，系最低要求；本技能执行收紧为 100%）：与目标技能的关键词/术语重叠、但真实诉求不同的查询。禁止明显无关的弱负例凑数（"天气""1+1"类，§6.2.5）。

## 二、正例四维覆盖（§6.2.2 / §6.2.3 / §6.2.10）

每条正例记录四维 `dims`：措辞（正式/口语/错别字/缩写）、显式度（点名/半点名/不点名）、详略（极简/中等/长带语境）、复杂度（单步/多步流程嵌入）。要求：

1. 四维至少各覆盖两档；点名与不点名都要有；
2. 注入真实语境：真实路径、人名/公司名、口语与错别字（§6.2.3）；
3. **优先"看不出关联"的边界样本**（§6.2.8）：查询措辞与技能术语零重叠、但诉求正落在技能核心价值上——它们承担真正的措辞差距检验；
4. 直白锚点（查询已明确索要技能所做的事）**少量保留 2–3 条**作基线校准：连它们都失败说明是管线问题而非描述问题；
5. 正例须有分量：至少 2–3 条为多步流程中嵌入的诉求，禁一步裸能力任务（§6.2.10）。

## 三、切分与冻结（§6.4.1–6.4.2）

- **train 12 / validation 8**（60/40），正负比例在两个子集内各自保持（train 6正/6负，validation 4正/4负）；
- 手工指定切分后**冻结**，禁随机重切（保证跨迭代可比）；
- 冻结 = 构造后立即计算 `frozen.sha256`；此后任何改动（哪怕一个字）视为**重新构造**，须记版本号并重置历史对比基线。

每条记录字段：`id`（P/N + 序号）、`subset`（train/validation）、`should_trigger`、`category`、`dims`、`context_features`、`query`（用户查询原文）、`rationale`（设计依据，供人工复核）。

## 四、负例设计要点

- 每条负例写明与哪个关键词重叠、真实诉求是什么（`rationale`）；
- 覆盖目标技能 description 中的**每一个高权重术语**至少一条负例——description 里写的每个"钩子词"都必须有 near-miss 检验它不会过度召回；
- 负例同样注入真实语境，避免"一眼假"。

## 五、自检清单（构造完成后逐条核对）

- [ ] 总量 20（±2），正负各 8–10
- [ ] 负例 100% near-miss，无弱负例凑数
- [ ] 正例四维各两档以上，边界样本 ≥5
- [ ] 直白锚点 ≤3 条
- [ ] train/validation 内正负比例保持
- [ ] description 每个高权重术语有对应负例
- [ ] 每条有 rationale 与 dims
- [ ] SHA256 已算并写入 frozen.sha256

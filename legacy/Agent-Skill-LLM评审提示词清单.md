# Agent Skill LLM 评审提示词清单（个人开发者版）

> **版本**：v1.4（2026-10-02；v1.3 固化为本地技能 `agent-skill-llm-review`（~/.workbuddy/skills/），技能优先、手工投喂为降级路径；v1.4 唯一正文变更 = W-08 补"S 关键词定位器缺位时由评审员自行定位"降级句——已同步技能 references/w-prompts.md，其余 28 条正文与 v1.2 逐字一致）
> **依据**：《Agent-Skill 生命周期验证方案》v1.3 中 LLM 评审（L 类）条目，经个人开发者裁剪
> **用法**：优先调用 `agent-skill-llm-review` 技能执行；技能不可用时，将待评审文件内容与对应提示词一起投喂 LLM；每条评审完成后按 V12 留痕。

---

## 0. 留痕与双评规则（V12 个人版，先读）

**每次评审在 `.verification/llm-review-log.md` 追加一行：**

```
| 日期 | 提示词编号 | 模型名+版本 | 输出证据（结论摘要/引用） | 判定 | 是否双评 |
```

**双评范围**：影响 [M] 级条目结论的关键判定必须两个独立会话或两个不同模型分别判定；评分不一致 → 升级人工裁决并记录理由。本清单中标注 ⚑ 的提示词属关键判定，默认双评。

**通用要求**（已内嵌各提示词）：逐条给结论，PASS/FAIL 必须引用被评审文本的具体位置作为证据；不确定时判 FAIL 并说明需要人工裁决的问题；不得泛泛而谈。

## 1. D 组 · 设计期

### D-01 取材材料提炼辅助（§5.1.4 辅助，仅辅助不替代人工裁决）

```text
你是技能取材分析助手。以下是原始材料（任务轨迹/项目文档/事故报告）：
<材料>
请提炼为结构化取材清单，分四类输出：
1. 奏效步骤：哪些做法被验证有效，证据在哪；
2. 纠正点：哪些做法曾出错、如何被纠正，证据在哪；
3. I/O 格式：输入输出格式约定，证据在哪；
4. 项目事实：具体的项目约束与事实，证据在哪。
每条必须标注来源（材料中的位置）。材料中不存在的类别明确写"无"，不得编造。
```

## 2. W 组 · 编写期语义评审

### W-01 frontmatter 语义（§2.1.4、§2.6.2–2.6.3、V16）

```text
你是 Agent Skill 评审员。评审以下 SKILL.md 的 frontmatter：
<frontmatter 内容>
逐条判定并给证据：
1. 字段是否依赖某个宿主私有的非标准字段（跨宿主不可用）？
2. metadata 键名是否彼此区分度足够、无冗余？
3. metadata/compatibility 是否被滥用（存放规避校验的内容、非必要信息）？
4. compatibility 声明是否均为必要（非必要不添加，V16）？
输出：每条 PASS/FAIL + 证据引用。任何 FAIL 给出修改建议。
```

### W-02 description 触发质量（§2.3.2–2.3.10、§6.1.1、V20）⚑

```text
你是 Agent Skill 触发评审员。以下是一个技能的 name 与 description（宿主加载时只读这两项）：
<name + description>
逐条判定并给证据：
1. 是否同时回答"做什么"和"何时用"，缺一即 FAIL；
2. 是否为第三人称祈使句/意图导向写法，无第一人称"我会/我将"；
3. 覆盖范围是否不窄不宽：具体功能 + 合适的触发关键词，既不漏触发场景也不泛滥；
4. "何时使用"的信息是否全部落在 description 内（用户只能靠它决定是否触发，不得寄望正文）；
5. 是否存在跨行 plain scalar 等写法风险（语义上是否一段连贯描述）。
输出：每条 PASS/FAIL + 证据。FAIL 时给出重写建议。
```

### W-03 compatibility 与运行器匹配（§2.5.2–2.5.5、V22）

```text
你是 Agent Skill 评审员。评审以下 compatibility 声明与脚本依赖：
<compatibility 字段 + scripts 依赖声明>
判定：
1. 每条声明是否必要、完整（运行时/运行器/网络需求是否都覆盖）；
2. 运行器选择（uvx/pipx/npx/bunx/deno/go run）是否与目标用户环境匹配、是否优先用了依赖自动解析的运行器；
3. 有无应声明而未声明的依赖或环境要求。
输出：PASS/FAIL + 证据 + 修改建议。
```

### W-04 渐进式披露（§4.1.1–4.1.2、§4.1.8–4.1.9、V18/V19）⚑

```text
你是 Agent Skill 结构评审员。以下是 SKILL.md 正文与 references/ 文件清单：
<SKILL.md 正文> <references 文件名与开头若干行>
判定：
1. 正文是否只保留每次运行必需的高频核心指令；大段参考材料是否已外移（正文整体会在激活后载入上下文，冗余即 FAIL）；
2. 被引参考文件是否不复述正文已有内容；
3. 多个同域参考文件是否按变体拆分且各自写明命中条件；
4. 独立的 Gotchas/参考文件是否有"当……时读取 <file>"的明确加载时机且触发信号足够明显。
输出：每条 PASS/FAIL + 证据。
```

### W-05 取材真实性（§5.1.1–5.1.2、§5.1.7、§5.1.8）⚑

```text
你是 Agent Skill 内容评审员。对照设计说明中的取材来源清单，评审以下正文：
<取材来源清单> <SKILL.md 正文>
逐段判定：
1. 是否含通识内容、默认行为复述、或模型本可直接读出的事实（有即 FAIL，正文应只写不显而易见的项目特定知识）；
2. 事实与决策是否清晰区分，无混写；
3. 规则是否采用"一句规则 + 反例"的压缩写法，无冗长解释。
输出：逐段结论 + 证据引用；列出所有疑似通识/默认行为段落。
```

### W-06 结构与详略（§5.2.4–5.2.6）

```text
你是 Agent Skill 结构评审员。评审以下正文的信息结构：
<SKILL.md 正文>
判定：
1. 详略是否得当：高频操作详细、低频操作从简，无均匀涂抹；
2. 正文结构是否清晰（工作流程、规则、示例分区明确）；
3. 有无内容游离于声明的技能范围之外。
输出：PASS/FAIL + 证据。
```

### W-07 约束校准（§5.3.1–5.3.3、§5.3.5–5.3.7）

```text
你是 Agent Skill 约束评审员。评审以下正文中的全部约束性语句（含 ALWAYS/NEVER/MUST/必须/禁止/一定）：
<SKILL.md 正文>
逐条判定：
1. 每条刚性约束是否给出理由（无理由的死命令即 FAIL）；
2. ALWAYS/NEVER 是否确有必要（是否为反模式滥用）；
3. 是否使用祈使句直接指示，无协商性、无"你应该考虑"式弱指令；
4. 约束是否校准：不过度限制正常工作路径。
输出：刚性语句清单 + 每条 PASS/FAIL + 证据。
```

### W-08 破坏性操作防护（§5.3.4，配合 S 关键词定位）⚑

```text
你是 Agent Skill 安全评审员。以下是正文中涉及破坏性操作的段落（脚本已定位）与对应脚本：
<定位段落> <相关脚本>
（若"定位段落"为空——即 S 关键词定位器不可用或未运行——则改为：请先自行通读上述脚本与正文，检索破坏性操作（删除/覆盖/迁移/发布/权限变更类），列出你定位到的段落再继续判定，并在输出开头注明"定位方式：评审员自定位（S 缺位降级）"。）
判定：每个破坏性操作的防护措施（确认标志/备份提示/作用域限制/dry-run）是否与风险相称。
过轻（高危无防护）或过重（低危操作要求多步确认拖累效率）均指出。
输出：逐操作 PASS/FAIL + 风险评级（高/中/低）+ 建议。
```

### W-09 默认值与泛化（§5.4.1–5.4.4）

```text
你是 Agent Skill 评审员。评审以下正文中的参数与方法描述：
<SKILL.md 正文>
判定：
1. 可设默认值的参数是否都给了合理默认；
2. 是否让 LLM 反问用户本可自行决定的事项（禁菜单反模式）；
3. 方法描述是否泛化可用而非绑定某个一次性场景。
输出：PASS/FAIL + 证据。
```

### W-10 Gotchas 质量（§5.5.1–5.5.2、§5.5.5、§5.5.7–5.5.8、V19）

> 注：本条中 V19（Gotchas 位置与加载时机信号是否足够明显）的语义判定已在 W-04 第 4 条覆盖且属 ⚑ 双评，本条单评即可，V19 相关结论以 W-04 双评结果为准，避免留痕时重复判定或口径漂移。

```text
你是 Agent Skill 评审员。评审以下 Gotchas 节及相关模板/清单：
<Gotchas 节 + 相关内容>
判定：
1. 每条 Gotchas 是否具体（含触发场景与正确做法），无泛化建议（"小心谨慎""注意安全"即 FAIL）；
2. 模板是否以真实模板给出而非文字描述；
3. 检查清单/验证循环是否确有必要（不是为凑结构而加）；
4. Gotchas 在正文中的位置是否靠近末尾（或独立文件已有明确加载时机）。
输出：逐条 PASS/FAIL + 证据。
```

### W-11 触发撰写原则（§6.1.2–6.1.9）

```text
你是 Agent Skill 触发评审员。评审以下 description 与触发相关设计：
<description + 相关说明>
判定：是否覆盖典型触发场景、排除不应触发的场景；表述是否意图导向；有无与相邻技能 description 的语义重叠导致串扰风险（对照相邻技能清单）。
输出：PASS/FAIL + 证据。（最终以 E 阶段触发回归实测为准，此处为预审。）
```

### W-12 用例真实感（§7.1.2–7.1.4、§7.1.7）

```text
你是评测集评审员。评审以下 evals.json 用例：
<evals.json>
判定：
1. 每条查询是否有真实语境感（像真实用户会问的话，无生造）；
2. 是否覆盖边界场景（正例之外是否有 near-miss 负例）；
3. 有无模糊提示（"测试一下"这类无信息量查询即 FAIL）。
输出：逐条 PASS/FAIL + 证据 + 修改建议。
```

### W-13 断言可验证性（§7.4.1–7.4.4）

```text
你是评测断言评审员。评审以下断言：
<断言列表>
逐条判定：
1. 是否可验证（有明确的判定依据，不是"效果要好"）；
2. 是否模糊（无量化/无具体检查点即 FAIL）；
3. 是否脆弱（对无关波动敏感，如要求精确措辞匹配）；
4. 范围是否恰当（不过宽不过窄）。
输出：逐条 PASS/FAIL + 证据 + 改写建议。
```

### W-14 脚本工程语义（§8.1.1、§8.1.3–8.1.6、§8.3.4）

```text
你是 Agent Skill 脚本评审员。评审以下脚本设计与错误消息：
<scripts 清单与关键片段 + 正文命令说明>
判定：
1. 是否重复造轮子（环境已有等价工具而自建）；
2. 前置条件声明是否完整（正文声称可跑的前提与脚本实际需求一致）；
3. 复杂多步命令是否已移入脚本而非堆在正文；
4. 错误消息文本是否含"错了什么 + 期望什么 + 下一步"。
输出：PASS/FAIL + 证据。
```

### W-15 安全语义审计（§9.1、§9.2、§9.7–9.9）⚑（必双评）

```text
你是 Agent Skill 安全审计员。对以下技能做全文恶意逻辑与一致性审计：
<SKILL.md 全文 + scripts/ 全部脚本 + 引用的外部端点清单>
逐项判定并给证据：
1. 是否存在恶意逻辑：数据外传、隐蔽后门、混淆代码、超出声明用途的行为；
2. 每个外部请求目标是否与 compatibility 声明及功能用途一致（用途一致性/最少惊讶）；
3. 正文是否有危险指令语义（绕过确认、静默上传、扩大权限）——关键词已扫描，请审语义变体；
4. 外网访问是否已在 compatibility 中声明；
5. 授权最小化初筛（§2.7.3）：allowed-tools 白名单与脚本实际用途逐一对照，有无超出用途的多余授权（为人工 M1-2 终审做初筛）。
输出：逐项 PASS/FAIL + 证据引用（文件+行/段）；任何可疑项标记为"需人工裁决"。
```

### W-16 术语、语言与可移植性（§11.3–11.4、§10.2）

```text
你是 Agent Skill 评审员。评审以下文本的术语与表达：
<SKILL.md 正文>
判定：1. 术语是否精确一致（同一概念全文同名，无近义漂移）；2. 表达是否机器可读优先（明确指令优于含糊描述）；3. 可移植性复核（§10.2，黑名单检索已扫，此处审语义残留与变体）：有无宿主专属路径/工具名以变体形式残留。
输出：PASS/FAIL + 证据。
```

## 3. E 组 · 测试期

### E-01 查询集质量（§6.2.8–6.2.9）

```text
你是评测集评审员。评审以下触发查询集：
<查询集>
判定：1. near-miss 负例质量（形似应触发但实际不应的查询是否真实、有区分力）；2. 每条查询的真实语境是否充分（能想象出具体使用场景）。
输出：逐条 PASS/FAIL + 证据 + 替换建议。
```

### E-02 无关键词照抄（§6.4.5）

```text
你是回归纪律审查员。对照以下两份材料：description 修改前后的 diff，与触发失败的查询列表：
<diff> <失败查询>
判定：修改后的 description 是否只是把失败查询的关键词原样抄入（过拟合信号）。
输出：PASS（无照抄）/ FAIL（列出照抄处）+ 证据。
```

### E-03 修订方向评审（§6.5.2–6.5.3、§6.5.9）

```text
你是技能优化评审员。以下是本轮 description 修订记录与评测结果：
<修订记录 + 结果>
判定：1. 修订是否朝"为什么没触发"的根因方向（而非表面加词）；2. 结构性问题时是否换了结构而非继续打补丁；3. 有无 pushy 写法（为提升触发率而堆砌宽泛关键词，牺牲精度）。
输出：PASS/FAIL + 证据 + 建议。
```

### E-04 语义断言评分（§7.5.1）⚑

```text
你是评分员。以下是技能的输出与对应的语义断言：
<技能输出> <断言列表>
逐条断言判定 PASS/FAIL。规则：PASS 必须引用输出中的具体内容作为证据；证据不足判 FAIL；不得凭整体印象打分。
输出：JSON 数组：[{"assertion": "...", "result": "PASS|FAIL", "evidence": "输出中的具体引用"}]
```

### E-05 断言难度复核（§7.5.4）

```text
你是评测设计评审员。以下是断言列表与首轮实际输出摘要：
<断言> <输出摘要>
判定：有无断言过易（任何合理输出都过）、过难（正确输出也过不了）、不可验证。
输出：逐条结论 + 证据 + 修订建议。
```

### E-06 盲评（§7.5.5）⚑

```text
你是盲评评委。以下是同一任务的两份匿名输出（版本 A / 版本 B），事先不知其来源：
<输出 A> <输出 B>
按以下维度独立评分（1–5 并给证据引用）：正确性、完整性、可用性。
输出：{"A": {...}, "B": {...}, "prefer": "A|B|tie", "reason": "..."}
（执行方注意：投喂前匿名化并随机排序，勿泄露版本对应关系；两份分别来自 with_skill / without_skill 或新旧版。）
```

### E-07 模式归因（§7.6.2）

```text
你是评测分析员。以下是断言通过情况矩阵（含仅带技能通过项清单）：
<矩阵数据>
判定：仅带技能通过的项中，价值归因是否真实由技能带来（而非任务波动或输出随机性）。
输出：逐项归因结论 + 证据。
```

### E-08 delta 解读（§7.6.4–7.6.5）

```text
你是评测分析员。以下是双跑对照数据（均值、波动、token/时长成本）：
<数据>
辅助解读：1. 当前波动水平下均值差异是否可信（样本少时明确说明置信不足）；2. 质量收益与成本（token/时长）是否成比例。
输出：分析结论 + "建议人工裁决点"清单（不代替人工拍板）。
```

### E-09 改进建议（§7.8.7）

```text
你是技能改进顾问。以下是三路信号：触发评测失败项、断言失败项、人工复核反馈：
<三路信号>
综合分析根因，输出 3–5 条具体改进建议，每条含：改什么文件、怎么改、预期解决哪个失败项。不输出泛泛建议。
```

### E-10 轨迹诊断（§5.1.9）

```text
你是轨迹诊断员。以下是技能运行轨迹与设计说明：
<轨迹> <设计说明>
按三类缺陷归因并给证据：1. 缺信息（正文缺该场景的必要指令）；2. 缺工具（缺脚本/资源）；3. 指令冲突（正文规则互相矛盾或与环境约束冲突）。
输出：缺陷清单（类别 + 位置 + 证据）+ 对应修改建议。
```

## 4. R 组 · 运行期

### R-01 纠错归纳（V10）

